# Salesforce sObjects are an open schema BY DEFINITION: the field names are the
# customer's org metadata, not ours, so extra="allow" is the vendor contract and
# extra="forbid" would reject every custom field (Custom_Field__c). The handler
# funnels through _extract_fields(), which takes either {"fields": {...}} or
# top-level keys. This is the one place in the fleet where an open body is right.
salesforce-api::POST /services/data/v59.0/sobjects/{sobject}::OPEN_BODY_SCHEMA
salesforce-api::PATCH /services/data/v59.0/sobjects/{sobject}/{record_id}::OPEN_BODY_SCHEMA

# The two read-shaped POSTs that used to sit here -- algolia POST
# /1/indexes/{index}/query and google-calendar POST /calendar/v3/freeBusy -- are
# GONE, tightened rather than blessed. They were excused on a blast-radius
# argument (an ignored search filter degrades to a wrong projection in the same
# response, never a lost write), not on a fidelity one, and the fidelity reading
# runs the other way: Algolia answers 4xx on an unrecognised search parameter
# (https://www.algolia.com/doc/rest-api/search/) and Google's JSON stack answers
# 400 badRequest "Invalid JSON payload received. Unknown name" for an unknown
# member (https://developers.google.com/calendar/api/v3/reference/freebusy/query).
# Forbidding is the faithful behaviour on both, so the residual-risk clause the
# old entry carried -- tighten if either search surface grows a filter an agent
# leans on -- was discharged instead of deferred.
